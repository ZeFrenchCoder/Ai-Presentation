# AWS VPC Networking Practice Questions

## Question 1: VPC Subnet Design
**Scenario:** You are designing a VPC for a three-tier web application that requires high availability across two Availability Zones. The application needs web servers, application servers, and database servers, with the database tier isolated from direct internet access.

**Question:** Which subnet configuration best meets these requirements?

A) Create 3 public subnets (one for each tier) across 2 AZs
B) Create 6 subnets: 2 public for web tier, 2 private for app tier, 2 private for database tier across 2 AZs
C) Create 4 subnets: 2 public for web/app tiers, 2 private for database tier across 2 AZs
D) Create 2 subnets: 1 public for web tier, 1 private for app/database tiers in single AZ

**Correct Answer: B**

**Explanation:**
- **Correct (B)**: This design provides proper network isolation with high availability. Each tier gets dedicated subnets in each AZ, allowing for proper security controls and fault tolerance.
- **Incorrect (A)**: Database servers should never be in public subnets for security reasons.
- **Incorrect (C)**: Application servers should also be in private subnets for security; they can receive traffic through load balancers.
- **Incorrect (D)**: Single AZ design doesn't provide high availability; mixing app and database tiers complicates security policies.

**Key Learning Points:**
- Always isolate database tier in private subnets
- Use multiple AZs for high availability
- Separate each tier for granular security control
- Public subnets should only contain resources that need direct internet access

## Question 2: Security Groups vs NACLs
**Scenario:** Your application is experiencing connectivity issues. Web servers in public subnets cannot communicate with application servers in private subnets on port 8080, even though the security group allows the traffic.

**Question:** What is the most likely cause and solution?

A) The Network ACL is blocking the traffic; modify the NACL to allow port 8080
B) The route table is missing a route; add a route for the private subnet
C) The Internet Gateway is blocking internal traffic; configure bypass rules
D) The security group is stateless; add both inbound and outbound rules

**Correct Answer: A**

**Explanation:**
- **Correct (A)**: NACLs are stateless and operate at the subnet level. If security groups allow traffic but connection fails, NACLs are likely blocking it.
- **Incorrect (B)**: Route tables within a VPC automatically include local routes for VPC CIDR; additional routes aren't needed for intra-VPC communication.
- **Incorrect (C)**: Internet Gateways don't filter internal VPC traffic; they only handle internet-bound traffic.
- **Incorrect (D)**: Security groups are stateful, not stateless; return traffic is automatically allowed.

**Key Learning Points:**
- Security groups are stateful (return traffic automatic)
- NACLs are stateless (must explicitly allow both directions)
- NACLs can block traffic even when security groups allow it
- Troubleshoot network issues in order: Security Groups → NACLs → Route Tables

## Question 3: Cross-VPC Communication
**Scenario:** Your company has two VPCs: Production VPC (10.0.0.0/16) and Development VPC (10.1.0.0/16). You need to enable communication between specific subnets in each VPC for database replication.

**Question:** What is the most secure and cost-effective solution?

A) Create a VPC Peering connection and update route tables with specific subnet routes
B) Set up a Transit Gateway and attach both VPCs with full routing
C) Use an Internet Gateway in each VPC and route traffic over the internet
D) Create a VPN connection between the VPCs using customer gateways

**Correct Answer: A**

**Explanation:**
- **Correct (A)**: VPC Peering provides direct, secure communication with granular routing control and lowest cost for two VPCs.
- **Incorrect (B)**: Transit Gateway is more expensive and designed for multiple VPC scenarios; overkill for two VPCs.
- **Incorrect (C)**: Internet routing is insecure and unnecessarily complex for internal communication.
- **Incorrect (D)**: VPN connections are for connecting to on-premises networks, not VPC-to-VPC communication.

**Key Learning Points:**
- VPC Peering is ideal for connecting two VPCs
- Transit Gateway is better for hub-and-spoke with many VPCs
- Always use private connectivity for internal communication
- Route tables must be updated after creating peering connections

## Question 4: NAT Gateway Troubleshooting
**Scenario:** Instances in your private subnet cannot access the internet for software updates, despite having a NAT Gateway configured in the public subnet. The NAT Gateway shows as "Available" in the console.

**Question:** Which configuration issue is most likely preventing internet access?

A) The NAT Gateway doesn't have an Elastic IP address assigned
B) The private subnet's route table doesn't have a route to the NAT Gateway
C) The public subnet's security group is blocking NAT Gateway traffic
D) The NAT Gateway is in the wrong Availability Zone

**Correct Answer: B**

**Explanation:**
- **Correct (B)**: Private subnets need a route to the NAT Gateway (0.0.0.0/0 → NAT Gateway ID) for internet access.
- **Incorrect (A)**: NAT Gateways require Elastic IP addresses and won't show as "Available" without one.
- **Incorrect (C)**: Security groups don't apply to NAT Gateways; they use NACLs for traffic control.
- **Incorrect (D)**: NAT Gateways can serve instances in any AZ within the same VPC.

**Key Learning Points:**
- NAT Gateways require routes in private subnet route tables
- NAT Gateways automatically get Elastic IP addresses
- Security groups don't apply to NAT Gateways
- One NAT Gateway can serve multiple AZs (though best practice is one per AZ for HA)

## Question 5: Route Table Priority
**Scenario:** You have a VPC with CIDR 10.0.0.0/16 and need to route traffic to 10.0.50.0/24 to a specific NAT instance, while other traffic goes to the standard Internet Gateway.

**Question:** How should you configure the route table?

A) Add route 10.0.50.0/24 → NAT instance, then 0.0.0.0/0 → Internet Gateway
B) Add route 0.0.0.0/0 → Internet Gateway, then 10.0.50.0/24 → NAT instance
C) Use two separate route tables with different priorities
D) Configure the NAT instance to forward traffic to the Internet Gateway

**Correct Answer: A**

**Explanation:**
- **Correct (A)**: More specific routes (longer prefix) take priority over less specific routes in AWS routing.
- **Incorrect (B)**: Order of entry doesn't matter; specificity determines priority. This would work but the explanation misunderstands routing logic.
- **Incorrect (C)**: Route priorities are determined by specificity, not separate tables or manual priorities.
- **Incorrect (D)**: This creates unnecessary complexity and doesn't address the routing requirement.

**Key Learning Points:**
- Most specific route (longest prefix match) wins
- /24 is more specific than /0, so takes priority
- Route order in table doesn't affect priority
- Use specific routes for exceptions, general routes for default behavior

## Question 6: VPC Endpoint Configuration
**Scenario:** Your application in a private subnet needs to access S3 buckets without internet access. You want to ensure traffic stays within the AWS network and doesn't incur NAT Gateway charges.

**Question:** What is the best solution?

A) Create a Gateway VPC Endpoint for S3 and update route tables
B) Create an Interface VPC Endpoint for S3 with DNS resolution
C) Configure a NAT Gateway with S3-specific routing rules
D) Use an Internet Gateway with security group restrictions

**Correct Answer: A**

**Explanation:**
- **Correct (A)**: Gateway VPC Endpoints for S3 are free, keep traffic on AWS network, and integrate with route tables.
- **Incorrect (B)**: Interface VPC Endpoints for S3 cost money per hour and per GB, unnecessary expense for S3.
- **Incorrect (C)**: NAT Gateway would work but costs money and traffic leaves AWS network.
- **Incorrect (D)**: Private subnets cannot use Internet Gateways directly.

**Key Learning Points:**
- Use Gateway VPC Endpoints for S3 and DynamoDB (free)
- Use Interface VPC Endpoints for other AWS services (paid)
- VPC Endpoints keep traffic within AWS network
- Gateway endpoints use route tables, Interface endpoints use DNS

## Question 7: Hybrid Connectivity Troubleshooting
**Scenario:** Your company has a Direct Connect connection to AWS, but resources in one specific subnet cannot reach on-premises systems, while other subnets work fine.

**Question:** What should you check first?

A) Direct Connect gateway configuration and routing
B) The subnet's route table for on-premises network routes
C) Virtual Private Gateway attachment to the VPC
D) Border Gateway Protocol (BGP) session status

**Correct Answer: B**

**Explanation:**
- **Correct (B)**: If other subnets work, the Direct Connect connection is functional; this is likely a subnet-specific routing issue.
- **Incorrect (A)**: Would affect all subnets, not just one specific subnet.
- **Incorrect (C)**: Would affect the entire VPC, not one subnet.
- **Incorrect (D)**: Would affect all connectivity, not subnet-specific issues.

**Key Learning Points:**
- Isolate network issues by scope (VPC-wide vs. subnet-specific)
- Check subnet route tables for missing on-premises routes
- BGP issues affect entire connection, not individual subnets
- Troubleshoot from specific to general when some resources work

## Question 8: Security Group Dependencies
**Scenario:** You have a web tier (port 80), application tier (port 8080), and database tier (port 3306). Each tier should only accept traffic from the tier above it.

**Question:** How should you configure the security groups?

A) Reference the source security group ID in each tier's inbound rules
B) Use IP address ranges for each tier in the security group rules
C) Create a single security group with all necessary ports open
D) Use NACLs instead of security groups for this requirement

**Correct Answer: A**

**Explanation:**
- **Correct (A)**: Security group references provide dynamic, secure access control that adapts as instances are added/removed.
- **Incorrect (B)**: IP ranges are static and require updates when instances change; less secure and harder to maintain.
- **Incorrect (C)**: Violates principle of least privilege; opens unnecessary access paths.
- **Incorrect (D)**: Security groups are more granular and easier to manage than NACLs for this use case.

**Key Learning Points:**
- Security group references are dynamic and secure
- Avoid hardcoding IP addresses when possible
- Implement defense in depth with proper tier isolation
- Security groups can reference other security groups

## Question 9: VPC Flow Logs Analysis
**Scenario:** You're investigating unusual network traffic and have enabled VPC Flow Logs. You notice many REJECT entries for traffic on port 22 from various internet IP addresses to your public web servers.

**Question:** What does this indicate and what action should you take?

A) Normal SSH brute force attempts; ensure strong passwords and consider disabling SSH
B) Internal application communication issues; check application configurations
C) VPC misconfiguration; review route table settings
D) DDoS attack in progress; immediately enable AWS Shield Advanced

**Correct Answer: A**

**Explanation:**
- **Correct (A)**: Rejected SSH traffic from internet IPs is typical brute force activity; REJECT means security groups are working correctly.
- **Incorrect (B)**: Traffic is coming from internet, not internal sources.
- **Incorrect (C)**: REJECT indicates security group/NACL blocking, not routing issues.
- **Incorrect (D)**: While concerning, this is typical background internet noise; DDoS would show much higher volume and different patterns.

**Key Learning Points:**
- REJECT in Flow Logs means security groups/NACLs blocked traffic (good)
- SSH brute force attempts are common internet background noise
- VPC Flow Logs help distinguish between routing and security issues
- Focus on security hardening rather than blocking all traffic

## Question 10: Multi-AZ VPC Design
**Scenario:** You're designing a VPC that spans 3 Availability Zones for a mission-critical application. You need public subnets for load balancers, private subnets for application servers, and isolated subnets for databases.

**Question:** What CIDR block allocation strategy provides the most flexibility for future growth?

A) /24 for each subnet (total of 9 /24 subnets)
B) /25 for each subnet (total of 9 /25 subnets) 
C) /26 for each subnet (total of 9 /26 subnets)
D) /23 for each subnet type (total of 3 /23 subnets)

**Correct Answer: B**

**Explanation:**
- **Correct (B)**: /25 provides 126 usable IP addresses per subnet, sufficient for most use cases while allowing room for additional subnets.
- **Incorrect (A)**: /24 (254 IPs) might be wasteful and limits total number of subnets you can create.
- **Incorrect (C)**: /26 (62 IPs) might be too restrictive for application tiers that need to scale.
- **Incorrect (D)**: Different subnet sizes add complexity and /23 (510 IPs) is likely excessive per subnet.

**Key Learning Points:**
- Balance IP allocation between current needs and future growth
- Consider AWS reserved IP addresses (5 per subnet)
- Uniform subnet sizing simplifies management
- Plan for subnet expansion and additional use cases
